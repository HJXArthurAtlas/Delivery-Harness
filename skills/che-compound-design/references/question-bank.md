# 四盲区问句库

## 用途与边界

本问句库用于需求澄清，按四个盲区逐项核对，避免遗漏会影响用户故事、验收标准或后续设计的需求信息。

- 问句是检查模板，不是必须逐字照问。根据当前需求替换页面名、字段名、角色、场景和动作。
- 问需求规则与业务结果，不预设实现方案。技能使用者已提出方案时，先澄清方案背后的目的与约束。
- 每个事项标记一个状态：`✅ 已有答案`、`❓ 需问人`、`🔍 可自查`。
- 每个事项记录结论、来源和适用的设计规约条目。规约未覆盖业务决策时，写「规约未规定，需由需求方确认」，不得用规约推断答案。
- 问句应按需求适用性核对。不适用时记录「不适用」及理由，不得静默跳过。
- 需求材料、代码和接口只用于确认已有事实；现状不等于正确口径。发现现状与技能使用者目标或设计规约冲突时，向技能使用者确认预期口径。
- 本问句库是需求层检查，不替代设计阶段依据 `设计自检.md` 进行的设计走查。

## 记录状态

| 状态     | 使用条件             | 记录要求                       |
| ------ | ---------------- | -------------------------- |
| ✅ 已有答案 | 需求材料已明确，或技能使用者已口头确认 | 记录结论与来源                    |
| 🔍 可自查 | 可从代码、接口、文档查到客观现状 | 记录查证事实与出处；如事实影响目标口径，仍需技能使用者确认 |
| ❓ 需问人  | 材料未说明，自查也无法确认    | 加入问题清单，等待技能使用者回答              |
| 不适用    | 该事项确实不适用于当前需求    | 说明不适用的原因，不作为未决项            |

## 规约关联说明

提问时按以下原则标注关联条目：

1. 能明确对应设计规约原则或模式的，注明具体编号，例如 `P3`、`P7`、`2.1`、`2.3`。
2. 规约没有定义该业务决策的，写「规约未规定，需由需求方确认」。
3. 不得为满足标注要求而牵强套用规约条目。
4. 问题清单中的每个问题都应附上关联条目或上述说明，并写明为什么必须问。

# 盲区①：为什么（业务目的与使用场景）

## 核心问题

- 这个需求要解决什么问题？目前用户遇到什么困难？
- 如果暂时不做，会对用户、业务或现有流程造成什么影响？
- 谁会使用？是否涉及不同角色、权限或使用场景？
- 用户通常在什么场景下使用？使用频率和时机是什么？
- 用户从哪里进入这个功能？进入前在做什么，完成后通常要做什么？
- 用户完成这件事后，什么结果才算成功？是否有可观察的行为或数据指标？
- 是否有明确的时间要求、业务约束或上线前提？

## 方案先行检查

当需求直接指定按钮、页面、弹窗、入口或交互方式时，继续确认：

- 这个方案要解决的具体问题是什么？
- 用户通过该方案希望完成什么结果？
- 哪些业务或技术约束使得该方案成为必要条件？
- 如果不采用这个方案，哪些目标或约束无法满足？

不要只确认“是否按这个方案做”，而要先理解方案背后的目的与必要约束。

## 按需追问

仅在答案会影响需求范围、验收或用户故事时追问：

- 为什么现在要做？是否有明确的业务节点或外部依赖？
- 本次需求明确不包含哪些内容？
- 是否有成功指标？若暂时没有，如何判断本次交付满足预期？
- 不同角色的目标是否不同？是否需要分别描述？

**关联规约参考**：可能涉及 `P1`（一屏一件事）、`P2`（状态先行）、`P7`（上下文可寻）；设计规约不定义业务目的、优先级和成功指标时，标注「规约未规定，需由需求方确认」。

# 盲区②：有哪些情况（状态全集与边界）

## 核心问题

- 这个页面、功能或业务对象有哪些状态？
- 用户分别在什么条件下进入每种状态？
- 状态之间如何变化？由用户操作、系统事件还是外部数据触发？
- 哪些状态可以逆转？哪些不能？状态变化后用户会看到什么结果？
- 是否存在无数据、无结果、无权限等不同情况？每种情况下用户能做什么？
- 操作失败、数据加载失败、网络不可用时，用户会看到什么？是否存在恢复路径？
- 是否有处理中、重复提交、超时、取消、部分成功等状态？

## 按需追问

### 数据和内容边界

- 空列表、单条数据、多条数据分别如何表现？
- 是否存在最大值、最小值、零值、负值或特殊格式？
- 文案、姓名、地址、编号等最长可能多长？超长时业务上要求如何处理？
- 是否存在重复数据、过期数据、数据不完整或部分字段缺失？
- 是否需要区分“没有数据”“没有匹配结果”和“无权查看”？

### 网络与异常

- 无网络或弱网时，用户能否继续当前操作？
- 请求超时、失败或返回部分数据时，业务上预期的结果是什么？
- 操作失败后是否允许重试？重试是否可能造成重复操作？
- 系统或外部服务暂不可用时，用户是否有替代流程？

### 状态来源与流转

- 是否已有状态名称、枚举值或状态流转规则？
- 是否存在不同来源对同一状态使用不同名称或口径？
- 状态变化后，哪些角色可以看到或执行后续操作？
- 是否存在并行状态、复合状态或状态更新延迟？

**关联规约参考**：空态可关联 `2.1`；页面当前状态与下一步可关联 `P2`；多步流程可关联 `P7`；失败反馈、网络降级等若规约未定义，标注「规约未规定，需由需求方确认」。

# 盲区③：数据算什么（字段口径与来源）

对需求涉及的每个关键字段逐项核对。不要因为界面上已有字段名，就假定字段含义和口径已经明确。

## 核心问题

- 字段的业务含义是什么？由谁维护或产生？
- 数据来自哪个系统、接口或用户输入？是否存在多个来源？
- 数值如何计算？是否涉及汇总、扣除、状态筛选或时间范围？
- 单位、精度、取整方式和时区是什么？
- 字段在什么情况下可能为空、缺失、为零或无效？
- 接口未返回该字段时，业务上应如何理解？
- 前端展示值是否需要转换、格式化或与其他字段组合？
- 后端、产品和业务方对该字段口径是否一致？

## 按需追问

### 列表、筛选与枚举

- 列表、筛选、Tab 或统计数字分别依据什么字段和条件？
- 可筛选的状态有哪些？是否有对应接口参数和枚举值？
- 当前接口是否支持需求要求的查询条件、排序和分页？
- 状态名称与接口枚举之间是否有明确映射？

### 隐私与差异

- 哪些字段需要脱敏？对不同角色或不同页面是否采用不同展示规则？
- 是否存在不同端、不同角色或不同业务场景下的字段差异？
- 是否有字段不能被记录、缓存或展示在特定场景？

### 口径查证

- 可否从接口定义、数据字典、现有实现或业务文档中确认现状？
- 查到的内容是已确认的业务规则，还是仅为当前实现？
- 若代码或接口现状与需求描述不同，预期口径以哪一方为准？

**关联规约参考**：字段缺失与 `0` 的区分、状态数据依据可关联 `P3`；数字单位、金额精度等若设计规约未定义，标注「规约未规定，需由需求方确认」，不得直接沿用既有页面或代码中的实现作为正确口径。

# 盲区④：动作的后果与回退（操作闭环）

## 核心问题

- 用户可以执行哪些动作？每个动作由什么条件触发？
- 执行动作需要满足哪些权限、业务状态或数据前置条件？
- 前置条件不满足时，用户需要知道什么原因或限制？
- 操作成功后，哪些业务数据或状态会改变？
- 操作结果由哪个系统确认？用户如何知道成功、失败或仍在处理中？
- 操作失败、超时或重复提交时，数据会发生什么？
- 操作能否撤销、恢复或重试？撤销的时限和影响是什么？
- 如果无法撤销，操作后果是否足够明确？是否需要额外防错？

## 按需追问

### 多步操作与中断

- 完成任务需要经过哪些业务步骤？每一步完成的条件是什么？
- 用户退出、返回、切后台或被电话打断后，流程和已填内容会怎样？
- 中断后能否继续？从哪里恢复？是否需要重新校验数据？
- 草稿、上传内容或未提交数据是否需要保留？

### 并发与重复操作

- 多个用户同时操作同一条数据时，业务上以哪个结果为准？
- 数据已被其他人修改或处理时，当前用户会看到什么？
- 重复点击、重复提交或网络重试是否可能造成重复扣款、重复创建或重复状态变更？
- 操作执行期间数据发生变化时，是否需要重新校验？

### 返回与后续流程

- 用户从哪些入口进入？操作完成或取消后应回到什么业务位置？
- 返回时已填写内容、筛选条件或列表位置是否需要保留？
- 操作完成后是否会触发通知、刷新、下一步任务或其他业务动作？

**关联规约参考**：输入前置拦截、撤销与防错可关联 `2.3`；中断恢复可关联 `2.4`；阻断决策与提示形式可关联 `2.5`；返回路径和多步进度可关联 `P7`。具体业务后果、权限和并发规则若规约未定义，标注「规约未规定，需由需求方确认」。

# 提问与记录规则

## 问题格式

每个需要技能使用者回答的问题应包含：

1. **明确、可回答的问题**；
2. **Why**：为什么不确认就无法确定需求、验收或后续设计；
3. **关联规约条目**：具体编号，或「规约未规定，需由需求方确认」；
4. **优先级**：`P0` 或 `P1`。

示例：

```md
### 盲区：数据算什么

- [P0] 接口未返回金额字段时，业务上应理解为“暂无金额”还是其他状态？
  - Why：该口径会影响缺失值展示和数据正确性，不能把未返回数据当作 0。
  - 关联规约：P3。
  - 状态：❓ 需问人
```
