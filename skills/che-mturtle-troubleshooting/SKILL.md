# 新赤湾线上问题排查

排查新赤湾体系内任意服务的线上问题。范围是**需要线上日志或数据库证据的排查**：异常报错、业务错误（状态不推进、数据缺失、结果与预期不符）、跨服务链路问题（API 调用、MQ、数据库、回调推送、workflow）。纯代码逻辑排查（不涉及线上数据）按普通开发流程处理。五个不变量先行记住：

1. **名称对号是你的事，不是用户的**：用户只会用口头名称描述目标（"中台财务"、"货运系统"、"开放平台"、"调度"、"TS"），可能附带业务凭证（单号/trace_id/时间点/账号），也可能什么都不给——有些问题本来就没有确切的业务数据关联。口头名称 → 哪个环境 → Loki 里的 namespace/app → 哪个数据库，由你按映射清单（`references/service-map.md` 名称对号总表）与自助发现判定，不要一上来就让用户提供技术信息。自助发现穷尽后仍无法锁定才提问（附上试过的路径和候选），这好过硬猜。本 skill 的存在意义就是压低用户的排查门槛。
2. **先定环境，再选工具**：正式环境就三个——生产（prod 集群）、UAT（uat 集群）、私有化（漳州集群，仅网运通/freight 部署）；另外 paas 有一个 stg 环境（`paas-stg`，服务独立部署但**与 prod 共用数据库**）。prod 集群里还混有其他 `*-stg` namespace、UAT 集群里混有 `-dev`/`-test`/`-auto` namespace——选错环境查出来的永远是空气，stg/dev 的日志不能当生产证据，但 paas-stg 共用 prod 库，它的数据写入是真实的生产写入。
3. **先懂业务，再核事实**：先判断问题落在哪个业务板块（支付/流水/订单/回调/调度……），结合服务映射与链路结构形成"正常流转长什么样、可能怎么坏"的预期，再去 Loki 和数据库找信息，两边互相印证。排查对象可能是报错，也可能是业务错误（状态不推进、数据缺失、结果与预期不符，日志里全是正常）——没有业务预期，后者根本看不见。
4. **声明证据边界**：日志级别、数据老化、数据源不含目标库（如当前 prod MySQL 实例只挂了 freight/dp_bi/newchiwan_bcdt，中台核心业务库不可见）、网关黑盒都会限制结论强度。结论里区分"已证实 / 推断 / 需对方核实"，比给出一个漂亮的错误结论有价值得多。
5. **视角跟着用户走，不依赖项目上下文**：判断要查哪些服务，依据是用户提到的系统名、业务现象、域名、单号等信号；当前工作目录只是弱信号之一，缺失时不影响排查——用户可以站在任何项目里，也可以在完全无关的目录提问。

## 第一步：名称对号（口头名称 → 环境 → namespace/app → 库）

排查的入口永远是：用户说的是哪个系统、哪个环境。按序用这些信号判定，全部对不上再问用户：

| 信号 | 例子 | 推断 |
| --- | --- | --- |
| 用户点名的系统/服务 | "中台的财务服务"、"开放平台"、"货运"、"TMS"、"调度" | 查名称对号总表（service-map.md）得到环境与 namespace/app |
| 环境词 | "生产/线上" → prod 集群；"漳州/私有化" → 漳州集群（同属**生产大类**）；"UAT/测试" → uat 集群（测试大类）；"stg" → `paas-stg`（paas 的 stg，服务独立、与 prod 共库） | 第一层先分生产 vs 测试，再定具体环境；用户没提环境时按业务现象默认生产，但要在结论里声明 |
| 业务凭证 | 单号、flow_no/transaction_no、trace_id、时间点、账号等 | 有凭证从凭证切入；没有就从现象 + 时间窗做广度扫描 |
| 报错域名 | `*.newchiwan.com`、`api.fjzwiot.com`（漳州）等 | 域名归属见 service-map.md 的 URL 前缀映射 |
| 当前工作目录 | 某个项目仓库 | 仅作弱信号；目录与问题无关或不在项目里时忽略 |

环境模型、MCP 工具识别、连接陷阱见 `references/environments.md`。关键事实：

- **prod 集群是新赤湾全公司所有服务的生产环境**；漳州集群是私有化部署（仅网运通/freight），私有化调用的中台接口**依然跑在 prod 集群**——跨环境调用两边工具都要用。paas 另有 stg 环境（与 prod 共库）。
- 每个环境需要两类 MCP 数据源：Loki（业务日志）和 MySQL（业务数据，通常只读）。以当前会话实际挂载的工具为准，按名字里的集群/环境段识别归属（如 zhanzhou → 漳州、prod → 生产、uat → UAT）。

## 前置检查：数据源齐备才开始

定位到目标环境后、进入主循环前，先把任务归入大类：**生产，还是测试（UAT）**。"漳州/私有化"属于生产大类（私有化生产），与 prod 一样按生产纪律对待；只有明确是 UAT/测试的才归测试大类。

然后对照会话实际挂载的 MCP 工具清单，逐项确认：目标大类下**每个相关环境**的 Loki 和 MySQL 数据源都已挂载。注意 MySQL 数据源是按实例挂载的，实例内可见的库有限（实测清单见 service-map.md 数据库一节）——目标服务的库不在任何已挂载实例里时，这本身就是一个要向用户声明的证据边界。

任何一项缺失，**在这里终止任务**，不要开始排查：

1. 明确告诉用户缺哪个环境的哪类数据源（或哪个库不可见）。
2. 由用户决定如何配置、挂载或恢复，处理完成后重新走本检查。
3. 绝不拿别的环境/别的数据源凑数，也不要在数据源残缺的状态下"先查一部分"——半套工具查出来的证据是残缺的，极易在收口时拼出似是而非的错误结论。

排查中途发现任务需要的环境当初没检查到，同样停下向用户说明，已查到的部分如实汇报为阶段性结果。

## 排查主循环

### 1. 理解问题，定位业务板块与链路

先分析用户说的是什么问题、落在哪个业务板块，再结合两份参考确定目标服务与数据面：`references/service-map.md`（名称对号总表、namespace/app/库映射、URL 前缀 → 服务归属、清单没有时如何自助发现）和 `references/cross-service.md`（调用通道、推送链结构、受理语义）。这一步的产出是两个预期，后续所有判断都基于它们：

- **正常流转长什么样**——对照基准；
- **可能怎么坏**——报错类（异常/超时/失败日志）与业务错误类（状态不推进、数据缺失、结果不符预期，日志里全是正常）都列出来。

### 2. 核事实：数据库与日志结合

带着模型去 DB 和 Loki 找信息，两边互相印证，而不是各查各的：

- **有业务凭证**（单号/trace_id/时间点/账号，任何一种）：从凭证定位具体记录 → 主表 → 状态字段 → 关联流水表 → 按时间线对日志。
- **没有凭证**：按模型定的"异常形态"做广度扫描——DB 查业务状态分布与缺失关联记录，Loki 验证关键事件是否发生；从结果里**自己挑一笔代表性异常样本**再单点深挖。广度回答"是不是、有多广"，样本回答"为什么"。

要点：

- **trace id 优先**：除漳州外，prod/UAT 环境的日志都带 trace id，且 newchiwan 系服务与开放平台之间已打通（极个别服务不统一）。排查跨服务问题时，**主动引导用户提供 trace id（request id）**——一个 id 能串起多个服务的完整链路，比任何单号都高效。
- `information_schema` 跨 schema 找表，不要假设表在默认库；目标库可能根本不在已挂载的 MySQL 实例里（见证据边界）。
- 同时查**一笔成功样本**做对照——它是"正常流转"的实证基准，没有对照就没有结论。
- 统计同类异常数量：只有 1 笔 → 个体问题（链路大概率是活的）；成批出现 → 系统性问题（优先查链路本身）。
- Loki label 约定与查询模式见 `references/environments.md`。0 行结果先二次判读（stream 存活、时间窗、数据老化）再下"从未发生"的结论。
- Loki 数据源 401：凭据权限问题，向用户报告并请其修复，期间继续推进数据库侧——排查不必被日志工具阻塞。

### 3. 收口结论

- 用时间线表格呈现：时间点 | 事件 | 证据（表记录/日志行）。
- 每个"没发生"的判断都给出验证方式（查过什么、返回 0 行、时间窗多大）。
- 建议落实到"找哪一方、核实哪个字段、用什么单号"，例如：让中台按 transaction_no 核实出款状态。
- 顺带发现的代码缺陷（静默吞状态、缺补偿任务、幂等缺失）单独列出，不与根因混淆。
